Fix the repeated work first

The sharpest performance cliff is in Git status, not rendering: one extra untracked file can turn every five-second refresh into a full content reread. The sharpest foreground stall is text layout. Orbit keeps the number of mounted messages small, but one message or one editor line can still exceed the entire frame budget several times over.

How to read the ranking   Recurrence, whether the user is blocked, and the availability of an isolated reproduction matter more than the largest millisecond value. These are triggered costs, not estimates of their prevalence in real sessions. No production behavior was changed.

The sessions-only control retains the same 10,000 main and 500 child session summaries, including one large unselected transcript; only the run table is emptied and the database repacked. On hardware, adding the historical assignments takes the median from 108 to 195 ms and from 50 to 80 MiB PSS. The corresponding deltas on the CPU-renderer stack are larger: about 260 ms and 51 MiB. These are whole-application deltas, including any differences in visible status rows, not an attribution of every millisecond or byte to the coordinator. That is not the price of drawing 50,000 rows. App::new synchronously loads the catalog and constructs the harness. Coordinator::load decodes every assignment and records it in a per-family map, including old terminal runs; result bodies are not eagerly decoded. Reading summaries, rebuilding the sidebar projection and driver initialization are also inside launch time.

Idle: 1 s after the first commit we took a five-second process CPU delta. The observed range across measured launches was 0.0–0.0% of one core (100 Hz tick accounting; one tick is about 0.2%). A zero delta is not proof of zero wakeups. No selected repository means no Git poll; no work means no activity-wave tick. RSS counts shared mappings in full, PSS apportions them; neither includes compositor memory or dedicated VRAM.

What the startup profile means. Five more empty CPU-renderer launches, killed after 1.5 s each, yielded 6,528 user-cycle samples at 499 Hz; 73.94% of sampled overhead was in LLVM and 6.61% in Lavapipe. Mesa shader caching was disabled in that stack. Do not optimize Rust session loading on the strength of an empty software-renderer profile, or attribute that profile to a hardware GPU.

Virtualization stops at the message boundary

The session example mounted 16 overscan/visible rows out of 20,000 at entry 15,000. Median indexed range lookup was 0.016 µs and incremental height append 0.060 µs. In the composer, the shape of a paste matters more than its byte count

At the tail of the repeated paragraph, the first typed character cost 22.96 ms, versus 0.03 ms on a new line after the many-line paste. Jumping to the beginning and inserting in the distinct-word fixture took 77.56 ms. In its median paste sample, native layout took 81.91 ms and the edit 0.17 ms; scrollbar measurement rounded to 0.000 ms. Moving undo bookkeeping off-thread is not the first fix.

A separate 957-sample cycle profile restricted to the distinct-word editor case put 9.52% in bidi property lookup, 8.92% in font fallback iteration and 8.86% in a ShapeLine::layout_to_buffer closure. This covers both mounted and unlaid cases and all edit phases, not just paste. Optimize paragraph-scale bidi/shaping/placement while preserving combining marks, directionality, selection offsets and undo; do not insert artificial newlines into the saved text.

An unchanged workspace can stay busy

Git status: one extra file defeats the warm cache

We exercised the real git::info path, including subprocesses and line counts, in one fresh committed repository. Each untracked file contained 8 KiB of ASCII text. We filled the current cache, polled four times, then added exactly one file at the end of the enumeration and polled four more times. The Git total was checked on every poll. No files changed during either series.

One continuous cache; process read-call bytes from /proc/self/io (rchar), not physical SSD reads.

The first over-capacity poll is deceptively fast: only the newly added file misses. It evicts the first file in scan order. On the next scan every miss evicts the file needed next. At five-second polling cadence this fixture accounts for about 768 MiB/min of extra logical reads while unchanged, even if the filesystem cache serves every byte. Timing only the first refresh after adding a file misses the cliff.

The LRU is shared across projects. git::read_info also runs sequential commands for the root, HEAD, branch, tracked numstat and untracked paths. On a hit, metadata is still checked; on a miss, counting reads the file. Captures run off the UI thread, coalesce per project and time out after 15 s. Prefer retaining a stable subset (e.g., admit after repeated use without displacing an entire scan), or a size-bounded per-project cache reconciled to membership and file versions. A bigger fixed LRU merely moves the boundary. Keep exact line counts, ignore rules and replacement detection.

Tool turns are sensitive to durable writes

A loopback WebSocket peer returned one real QuickJS call, accepted its result on a chained request, streamed 64 text deltas and completed the answer. No remote inference or artificial think time. The stopwatch starts before starting one or eight main conversations on the same harness and ends after every turn finishes; the final saved answer is then checked. This is group makespan, including peer framing, scheduling, startup work per turn and persistence—not time to first token, agent throughput in production or pure SQLite time.

The eight-turn gap between storage targets is ~131 ms vs ~20 ms for one. This implicates the storage path under concurrency; it does not prove the entire gap is lock contention. SQLite uses WAL and synchronous=FULL. Tool-start and result boundaries must survive crashes, and saves are already offloaded from async execution. Record time waiting for the connection separately from transaction and sync time. Test coalescing redundant ordinary saves, not accepting or starting side effects before their commit.

Where local computation ends and service latency begins

Nine warm-process probes measured 0.69 ms median for a fresh cell emitting text, and 2.01 ms for a fresh cell spawning /bin/sh to run printf. These exercise the runtime with a no-op transcript observer; durable tool events are included instead in the loopback-turn experiment. The timer fixture recorded zero process CPU ticks during one second of waiting in all six runs. Neither the JS interpreter nor timer polling looks like the first target for short tools.

On the wire, reuse of previous_response_id slices off unchanged items before media projection. Locally the prefix is still compared, and prior tool-call IDs are collected by scanning history; the checkpoint shares its persistent input tree, not a deep clone. At a cold reconnect, full input must be materialized and serialized. Native compaction may serialize a large candidate request to estimate size; fallback chunks and archives unsummarized entries. These are source-supported scaling risks, not measured service delays. Instrument item counts, frame bytes, prepare time and fallback frequency before changing continuation logic.

Image preparation can queue unrelated work

The image probe feeds deterministic noisy JPEG bytes to the real media store. Each import uses a new directory so content-addressed files do not accidentally turn later writes into hits. Creation of the input JPEG is excluded. The second stage projects the stored media reference to an input-image data URL and serializes a minimal provider frame; it does not send that frame.

A 4K import takes ~0.33 s before the attachment is ready. The file import runs on the single UI I/O worker; a selection or draft save queued behind it can inherit the remaining wait even though the window thread itself is free. MediaStore::image holds a process-wide decoder lock across validation, durable original/prepared/thumbnail writes and PNG encoding. The stage timings measure the whole operation, not which codec subroutine dominates. The queue effect is inferred from its scheduling, not a measured click delay.

Prepared PNG, base64 string and serialized JSON can coexist; the 31.65 MiB wire-string length is not a peak heap estimate. A full reconnect can repeat projection, unlike a successful suffix continuation. Actual screenshots often compress far better than this stressor. Bound worker concurrency by decoded memory, not merely image count; preserve original bytes, hash identity, orientation, deletion leases and atomic saves.
